# tools/headless.ts — 헤드리스 대량 시뮬레이션 / 밸런싱 CLI

브라우저 없이 전투 시뮬레이션과 육성 루프(10일 × 5스텝)를 돌려 밸런싱 수치를 뽑는 도구입니다.
`src/core/**` 만 사용하며 DOM 을 건드리지 않습니다. 외부 라이브러리 의존성은 없고 `tsx` 로 바로 실행합니다.

```
npm run headless -- [옵션]
```

`npm run headless` 뒤의 `--` 는 npm 이 옵션을 스크립트에 넘기도록 하는 구분자입니다. 빠뜨리면 옵션이 무시됩니다.

하루 구성(고정): **1선택 · 2선택 · 3몬스터 · 4선택 · 5전투** → 하루 마무리(`day_end`) → 다음 날. 총 10일.

## 옵션

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--games N` | 100 | 시뮬레이션할 판 수 (기본 모드) |
| `--seed S` | 1 | 루트 시드. 같은 시드 + 같은 옵션이면 결과가 완전히 같음 |
| `--map M` | random | `plains` / `dark` / `desert` / `glacier` / `random`. random 이면 판마다 시드에서 파생해 선택 |
| `--day D` | 5 | 양 팀을 `generateOpponentTeam` 으로 만들 때의 육성 일차 (1~10). 1 은 갓 뽑은 팀, 10 은 완성 팀 수준 |
| `--cycle D` | – | `--day` 의 옛 이름. v0.3 스크립트 호환용 별칭이며 동작은 완전히 같음 |
| `--runs N` | 60 | `--monster` / `--rarity` 에서 쓸 표본 육성 수. 시드 `S`, `S+1`, … `S+N-1` |
| `--policy P` | greedy | 육성 자동 정책. `greedy` / `first` / `random` |
| `--determinism` | – | 같은 입력으로 전투를 두 번 돌려 틱마다 프레임 해시를 비교 |
| `--growth` | – | 10일 × 5스텝 육성을 자동 정책으로 끝까지 진행하고 분화 보장을 검증 |
| `--monster` | – | 매 일차 하급·중급·고급을 모두 싸워 난이도별 승률표를 뽑음 (난이도 보정 도구) |
| `--rarity` | – | 선택지 등급 분포·등급별 예상 전투력 상승치·보장 등급 동작 검증 |
| `--json` | – | 표 대신 요약 JSON 을 stdout 에 출력 (다른 도구에 넘기기 좋음) |
| `--help` | – | 도움말 |

`--games=200` 처럼 `=` 로 붙여 써도 됩니다.

### 자동 정책 (`--policy`)

| 정책 | 선택지 | 몬스터 난이도 | 보너스 상점 |
|---|---|---|---|
| `greedy` (기본) | `estimatePowerDelta` 가 가장 큰 카드 (동점이면 앞 카드) | 항상 **중급** | 싼 스킬부터 하루 최대 2개 구매 후, 남은 포인트를 전부 스탯 훈련에 사용 |
| `first` | 항상 0번 카드 | 항상 첫 카드(하급) | 구매 없음 |
| `random` | 시드에서 파생한 난수로 선택 | 난수로 선택 | 구매 없음 |

`greedy` 가 GDD 에서 말하는 "표준 성장 플레이어"에 해당합니다. 몬스터 난이도 보정(`--monster`)은 항상 `greedy` 로 돕니다.

`greedy` 의 상점 정책은 포인트를 남기지 않습니다(성장 곡선 실측용). 이 정책을 바꾸면 기준 플레이어의
전투력 곡선이 통째로 바뀌므로 `monsters.ts` 의 `EXPECTED_TEAM_POWER_BY_DAY` 와
`charGen.ts` 의 `OPPONENT_POWER_BY_DAY` 를 반드시 다시 측정해야 합니다.

기준 팀 구성(`pickDistinctJobs`)은 **탱커 또는 힐러 1명을 먼저 넣고** 나머지를 서로 다른 직업으로 채웁니다.
`generateOpponentTeam` 이 3일차부터 상대에게 같은 보장을 주기 때문에, 기준 플레이어만 보장이 없으면
표본의 3분의 1이 구조적으로 불리해져(탱커 없는 팀의 5:5 승률이 24%p 낮았습니다) 모든 난이도 보정값이
그 편향 위에 맞춰집니다. 이 규칙을 바꿀 때도 위 두 표를 다시 측정하세요.

## 1. 대량 전투 (기본 모드)

```
npm run headless -- --games 200 --seed 1
npm run headless -- --games 500 --map desert --day 10
npm run headless -- --games 1000 --json > result.json
```

판마다 `hashSeed("시드:판번호:A")`, `...:B`, `...:battle`, `...:map` 으로 시드를 파생하므로
판 수를 늘려도 앞쪽 판의 입력은 바뀌지 않습니다 (`--games 100` 의 1~100판 = `--games 200` 의 1~100판).

출력 표:

- **전체 결과**: A 승 / B 승 / 무승부 비율, 평균 전투 시간(초).
  두 팀 모두 같은 방식으로 생성되므로 A 와 B 승률이 크게 다르면 스폰 위치나 진영 처리에 편향이 있다는 뜻입니다.
- **맵별 A 승률**: 맵별 판수, A/B/무승부 비율, 평균 시간.
- **직업별**: 메인 직업마다 등장 횟수(캐릭터 단위), 승률, 무승부 비율, 평균 피해량, 평균 회복량, 생존율,
  평균 킬, 평균 스킬 사용 횟수. 승률 내림차순. 소환물의 피해·회복·킬은 `summon` 이벤트의 소환사에게 합산됩니다.
- **스킬 사용 상위 10**: `skill` 이벤트 기준 사용 횟수와 판당 횟수.
- **종료 사유**: `annihilation` / `timeout_hp` / `capture` / `timeout_draw` 등의 히스토그램.

20판 이상이면 진행률을 stderr 에 표시합니다 (`--json` 일 때는 표시하지 않음).

## 2. 결정론 검증

```
npm run headless -- --determinism --seed 3 --map glacier --day 8
```

`--seed`/`--map`/`--day` 로 만든 0번 판의 입력을 JSON 으로 두 번 복사해 시뮬레이터 두 개를 만들고,
틱마다 `step()` 결과(유닛 스냅샷, 이벤트, 거점 상태, 종료 플래그)를 직렬화한 FNV-1a 해시를 비교합니다.

- **프레임 해시 비교**: 첫 불일치 틱과 어느 유닛의 어느 필드가 달랐는지 출력.
- **최종 결과 비교**: `result()` 직렬화 비교.
- **입력 불변 검사**: 시뮬레이터가 `BattleInput` 객체를 수정했는지 검사 (경고만, PASS/FAIL 판정에는 포함하지 않음).

모두 통과하면 `결과: PASS`, 종료 코드 0. 실패 시 종료 코드 1 이므로 CI 에서 쓸 수 있습니다.

## 3. 육성 헤드리스 (`--growth`)

```
npm run headless -- --growth --seed 1
npm run headless -- --growth --policy random --seed 42
npm run headless -- --growth --seed 42 --json
```

`src/core/growth/run.ts` 상태 머신을 `--policy` 정책으로 10일 × 5스텝 끝까지 진행합니다.

1. 풀에서 앞에서부터 서로 다른 메인 직업 5명을 고른다 (팀 이름 "헤드리스 검증팀").
2. 선택 스텝(1·2·4)은 정책대로 카드 한 장을 고른다.
3. 몬스터 스텝(3)은 정책대로 난이도를 고르고 전투는 `runToEnd()` 로 즉시 끝낸다.
4. 전투 스텝(5)도 `runToEnd()`.
5. 하루 마무리에서 (greedy 라면) 싼 스킬부터 최대 2개를 사고, 남은 포인트를 스탯 훈련에 전부 쓴 뒤 다음 날로 넘어간다.

출력:

- **일차별 진행**: 일차, 5:5 맵, 그날 고른 카드 3장의 등급, 몬스터 난이도와 승패, 5:5 승패,
  그날 획득한 포인트, 팀 평균 스탯합, 팀 전투력(팀원 `powerRating` 합).
- **일차별 고른 선택지**: 몬스터 종류 이름과 고른 카드 제목 (도박형은 성공/실패 표시).
- **요약 줄**: 5:5 전적, 몬스터 전적, 총 획득 포인트, 상점에서 산 스킬 수, 남은 포인트,
  최종 평균 스탯합/전투력, 보장 등급(`rarityFloor`) 충족 횟수(PASS/FAIL).
- **직업 분화 보장 검증**: 캐릭터마다 예정 일차(`RunState.subJobChoiceDay`), 분화 선택지가 실제로 등장한
  `(일차:스텝)`, 직업 변경 이력, 최종 세부 직업, PASS/FAIL 과 실패 사유.
  판정 기준은 **첫 등장이 4~6일차 안**이고, 다른 날 다시 등장한 경우는
  (a) 그때까지 아직 분화하지 않았다면(정책이 다른 카드를 골라 보장이 이어진 경우) 정상,
  (b) 이미 분화한 상태였다면 **그 사이에 직업 변경이 있었을 때만**(재분화) 인정합니다.
  등장 표기는 `일차:스텝` 이고 뒤의 `*` 는 이미 분화된 상태에서 다시 제시되었다는 뜻입니다.

모든 캐릭터가 PASS 이고 10일차가 `done` 까지 도달하면 종료 코드 0, 아니면 1.

### 5:5 상대 강도 보정

`--growth` 를 시드를 바꿔가며 여러 번 돌려 일차별 5:5 승률을 보고 `charGen.ts` 의
`OPPONENT_POWER_BY_DAY` (일차별 상대팀 목표 전투력)를 조정합니다. `generateOpponentTeam` 은 팀을 만든 뒤
`fitTeamPower` 로 이 목표치에 스탯을 맞추므로, 상대 강도 곡선은 그 표 하나로 결정됩니다.
목표는 표준 성장 플레이어 기준 일차별 50% 안팎이고, 현재 실측은 시드 1~32 에서 일차별 44~56% / 전체 50.6% 입니다.

## 4. 몬스터 난이도 보정 (`--monster`)

```
npm run headless -- --monster --runs 60
npm run headless -- --monster --runs 200 --seed 100 --json > monster.json
```

`greedy` 정책으로 `--runs` 회의 표준 육성을 돌리면서, **매 일차 3스텝마다 하급·중급·고급 세 장을 전부 싸워 봅니다.**
싸움에는 팀과 몬스터 편성의 깊은 복사본만 쓰고 전투 시드도 따로 파생하므로(`hashSeed("시드:일차:probe:난이도:몬스터id")`)
진행 중인 육성 결과는 전혀 바뀌지 않습니다. 실제 진행은 그대로 중급을 골라 이어집니다.

출력:

- **일차 × 난이도 승률**: 각 칸은 `승률 (평균 전투 시간)`. 후반 일차에서 난이도가 따라 올라가는지 여기서 봅니다.
- **난이도별 전체 승률과 목표**: 목표(하급 95~100% / 중급 80% / 고급 50%)와의 차이를 `+xx.xp` 로 표시하고,
  하급은 95% 이상, 중급·고급은 오차 ±5%p 안이면 `OK`, 아니면 `조정 필요`.
- **난이도별 전투 시간 분포**: 평균·중앙값·40초 미만 비율·120초 초과 비율. 평균만 보면 긴 꼬리에 가려
  중앙값이 목표 하한(40초) 아래로 내려간 것을 놓치므로, 판정은 중앙값과 두 비율로 합니다.
- **몬스터 종별 승률과 전투 시간**: 종마다 승률·평균·중앙값·120초 초과 비율. 난이도 평균은 맞는데
  특정 종만 크게 벗어나는 경우를 여기서 잡고, 그 종의 `MonsterDef.powerScale` 만 움직입니다.
- **팀 전투력** 열: 그 일차 3스텝(몬스터 전투 직전)의 실측 평균 팀 전투력.
  `monsters.ts` 의 `EXPECTED_TEAM_POWER_BY_DAY` 는 이 열을 그대로 옮겨 적은 값입니다.

보정 순서는 이렇습니다.

1. **일차별 기울기**를 먼저 잡는다 — `EXPECTED_TEAM_POWER_BY_DAY` 를 위 '팀 전투력' 열로 갱신하고,
   그래도 남는 기울기는 `DAY_DIFFICULTY_EXPONENT` 로 다듬는다 (현재 하급·중급 0.17 / 고급 0.37).
2. **전체 수준**을 맞춘다 — `TIER_POWER_RATIO` (현재 하급 0.62 / 중급 0.845 / 고급 0.993).
3. **종별 편차**를 맞춘다 — `MonsterDef.powerScale`, `MonsterUnitTemplate.derivedMult`.

승률은 전투력에 매우 민감합니다(1% → 4~6%p). 한 번에 0.01~0.02 씩만 움직이고 매번 다시 측정하세요.
시드군만 바꿔도 ±5%p 는 움직이므로 최소 두 시드군에서 확인해야 합니다
(예: `--runs 40 --seed 1` 과 `--runs 40 --seed 201`).

전투 수가 많습니다. `--runs 60` 이면 난이도 시험 1,800판 + 실제 육성 전투 1,200판이고,
측정 기준 약 30초 걸립니다 (`--runs 200` 은 1분 30초 안팎). 진행률은 stderr 에 표시됩니다.
표본 60회면 난이도당 600판이라 승률 오차가 ±2%p 수준입니다.

## 5. 선택지 등급 모델 검증 (`--rarity`)

```
npm run headless -- --rarity --runs 60
npm run headless -- --rarity --runs 200 --json > rarity.json
```

전투 없이 `generateChoices` 를 일차 1~10 × 선택 스텝 1·2·4 로 반복 호출해 대량의 카드 표본을 만듭니다
(`--runs 60` 이면 60팀 × 30세트 = 분포용 1,800세트 / 5,400장). 세트마다 보장 등급을 건 세트를 한 번 더
생성해 `rarityFloor` 동작을 따로 검증합니다 — 보장을 건 세트는 상위 등급이 섞이므로 분포 표본에는 넣지 않습니다.
분화 보장이 분포를 가리지 않도록 표본 생성 시 `subJobChoiceDay` 는 비웁니다(분화 보장 자체는 `--growth` 가 검증).
`generateChoices` 를 부를 수 없으면 실제 육성을 돌려 제시된 세트를 모으는 방식으로 자동 전환합니다(느림, stderr 에 안내).

출력:

- **일차 구간별 등급 분포**: `관측 % / 기대 %`. 기대값은 GDD §7.4.1 의 가중치
  (1~3일 52/32/13/3, 4~7일 44/34/17/5, 8~10일 34/35/22/9).
- **등급별 powerDelta 와 스탯 상승량**: 카드 수, 비율, 평균/최소/최대 `powerDelta`,
  평균 총 스탯 상승량과 GDD §7.4.2 기준값(일반 10~16 / 레어 20~30 / 에픽 36~50 / 전설 60~85).
  스탯 상승량은 순수 스탯 카드(집중·합동·편중·도박)의 **순 변화량(상승 − 하락)** 입니다. 하락을 빼지 않으면
  편중 훈련처럼 위험을 지고 상승을 부풀린 카드가 기준을 넘은 것처럼 보입니다. 스킬·시너지·분화·맵 적응·희생은
  보상이 스탯만이 아니라 제외합니다.
  `powerDelta` 는 `estimatePowerDelta(team, choice)` 로 계산합니다 (스탯 1 = 1, 스킬 = 25, 시너지 = 20, 분화 = 35, 맵 적응 1 = 0.4).
  등급이 올라갈수록 평균 `powerDelta` 가 커지고 레어 이상의 **최소값이 음수가 아니어야** 합니다
  (카드 색이 값을 과장하면 안 됩니다). 등급 예산 밖의 '직업 변경' 카드만 예외로 항상 일반이며 음수일 수 있습니다.
- **선택지 종류별**: 종류마다 등장 비율, 평균 `powerDelta`, 최빈 등급.
- **보장 등급(`rarityFloor`) 검증**: 레어/에픽/전설 보장을 걸었을 때 세트 3장 중 최소 1장이
  그 등급 이상이었는지. 하나라도 어기면 FAIL 이고 종료 코드 1 입니다.

분화 보장 세트(한 캐릭터의 세부 직업 3장)는 분포를 왜곡하므로 표본에서 빼고 개수만 따로 셉니다.
'직업 변경' 카드는 희귀도 롤을 거치지 않는 특수 카드(세트당 최대 1장, 낮은 확률)라 일반 등급 비율을 1%p 정도 밀어 올립니다.

## 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 정상 (검증 모드는 PASS) |
| 1 | `--determinism` / `--growth` / `--rarity` 검증 실패, 또는 실행 중 오류 |
| 2 | 잘못된 옵션 |

`--monster` 는 측정 도구이므로 목표 승률을 벗어나도 0 을 돌려줍니다.

## 시드 파생 규칙

전부 `src/core/rng.ts` 의 `Rng` 와 `hashSeed` 만 사용합니다. `Math.random`, `Date` 는 쓰지 않습니다.

| 용도 | 시드 |
|---|---|
| 판 g 의 맵 (`--map random`) | `hashSeed("S:g:map")` |
| 판 g 의 팀 A / B | `hashSeed("S:g:A")` / `hashSeed("S:g:B")` |
| 판 g 의 전투 | `hashSeed("S:g:battle")` |
| 육성 모드 | `newRun(S)` 이후는 run.ts 가 `hashSeed("S:일차:용도")` 로 파생 |
| `random` 정책의 카드/난이도 선택 | `hashSeed("S:일차:스텝:choice")` / `...:monster` |
| `--monster` 의 난이도 시험 전투 | `hashSeed("S:일차:probe:난이도:몬스터id")` |
| `--rarity` 의 선택지 생성 | `hashSeed("S:일차:스텝:rarity")` |
| `--rarity` 의 보장 등급 검증 세트 | `hashSeed("S:일차:스텝:floor:등급")` |

같은 옵션이면 몇 번을 돌려도 출력이 완전히 같습니다.

## 구현 메모

- 육성 모듈(`run.ts`, `choices.ts`)은 육성 모드에서만 **동적 import** 합니다. 육성 쪽이 수정 중이어도
  `--games` / `--determinism` 은 그대로 동작합니다.
- 상태 머신 함수는 이름 후보 목록으로 찾습니다(`pickChoice` / `pickMonster` / `finishMonsterBattle` /
  `finishDay` 등). 이름이 달라 못 찾으면 "시도한 이름" 을 한국어로 알려줍니다.
  `estimatePowerDelta` 가 없으면 카드의 `Choice.powerDelta` 값을 대신 씁니다.

## 활용 팁

- 직업 밸런스: `--games 1000 --day 10` 으로 완성 팀 기준 승률 표를 보고, 50% 에서 크게 벗어나는 직업의
  `statProfile`/스킬 계수를 조정합니다.
- 맵 밸런스: `--map` 을 바꿔가며 종료 사유 분포를 봅니다. 사막에서 `timeout_hp` 가 대부분이면 제한시간이 짧거나 피해량이 낮은 것입니다.
- 몬스터 밸런스: `--monster` → `powerScale`/`derivedMult` 수정 → 다시 `--monster`. 일차별 표에서 특정 구간만
  꺼진다면 일차 스케일링 곡선을, 전 구간이 고르게 낮다면 `powerScale` 을 손봅니다.
- 보상 균형: `--growth --json` 의 `days[].pointsEarned` 합과 `finalTeamPower` 로 몬스터 보상이 5:5 보상을 압도하지 않는지 봅니다.
- 시뮬레이터를 고친 뒤에는 항상 `--determinism` 을 한 번 돌려 순회 순서나 부동소수점 문제로 결정론이 깨지지 않았는지 확인합니다.
- 결과를 비교할 때는 `--json` 출력을 파일로 저장해 두고 diff 하는 것이 편합니다.
